# 现货数据库撮合

本文档记录币安普通现货成交的数据库 FIFO 撮合、底仓锁定和统计读取口径。当前范围只包含普通现货平仓；币本位合约对冲撮合暂未纳入本流程，U 本位合约不再作为新开仓场景考虑。

## 1. 设计目标

原统计逻辑在内存 Map 中临时撮合买卖成交。同一批历史成交每次查询都要重新计算，后续数据或规则变化也可能让历史持仓归属发生变化。

现在将撮合结果写入数据库：

- 买卖成交按 FIFO 规则撮合。
- 已完成的买卖对应关系保存为明细，不在查询统计时重新分配。
- 每笔原始成交保存累计撮合数量、剩余数量和状态。
- 被标记为底仓的买入数量不参与普通现货平仓撮合；解除底仓后，释放数量可继续参与后续撮合。
- 现货统计直接读取数据库撮合结果和剩余持仓。

## 2. 数据表职责

### `binance_spot_trade_match_state`

每笔 `binance_trade_info` 现货成交对应一条撮合状态，保存原始数量、已撮合数量、剩余数量和撮合状态。

状态含义：

- `PENDING`：尚未撮合。
- `PARTIAL`：已部分撮合，仍有剩余数量。
- `COMPLETED`：已全部撮合。
- `EXCEPTION`：卖出成交没有足够的历史可用买入数量完成撮合。

当前阶段沿用项目已有约束，以 `trade_id` 作为状态表唯一标识；多账户出现真实成交 ID 冲突时再扩展联合唯一键。

### `binance_spot_trade_match`

保存每一段已经确定的 FIFO 撮合明细，包括买入/卖出成交 ID、数量、价格和时间快照，以及已实现盈亏、手续费和净盈亏。

手续费暂按买卖金额合计的 `0.1%` 计算：

```text
pnl = sellAmount - buyAmount
fee = (buyAmount + sellAmount) × 0.001
netPnl = pnl - fee
```

### `binance_spot_core_position`

保存指定买入成交中被锁定为底仓的数量。`released_at` 为空表示仍然有效；解除后保留历史记录，不直接删除。

一个买入批次设置的底仓数量不能超过该批次当前剩余持仓数量。已经完全卖出的买入成交不能再设置为底仓。

建表脚本：

- `sql/binance_spot_trade_match.sql`
- `sql/binance_spot_core_position.sql`

## 3. FIFO 撮合规则

撮合范围由 `uid + symbol` 确定，不跨账户、不跨交易对。

1. 卖出成交按 `trade_time ASC, trade_id ASC` 处理。
2. 每笔卖出只能匹配发生在它之前的买入成交；时间相同时，买入 `trade_id` 必须小于卖出 `trade_id`。
3. 可用买入成交同样按 `trade_time ASC, trade_id ASC` 处理。
4. 单批买入可用数量为 `remaining_qty - active_core_qty`。
5. 每次取买入可用数量和卖出剩余数量的较小值，写入一条撮合明细，并同步更新双方状态。
6. 整个初始化和撮合过程在事务中执行，相关待处理记录使用数据库行锁。

底仓不会改变 FIFO 规则，它只会暂时减少对应买入批次的可用数量。解除底仓后，原批次按自身原始时间顺序重新成为可用候选。

## 4. 触发方式

正常入口是现货成交同步。每次指定账户、交易对的现货成交同步完成后，系统自动执行：

1. 将尚未进入状态表的原始成交初始化为 `PENDING`。
2. 对当前范围内可处理的卖出成交执行数据库 FIFO 撮合。

也可以通过以下接口手动补执行：

```text
PUT /api/binanceTradeInfo/matchSpotTradeInfo?uid={uid}&symbol={symbol}
```

接口要求 `binanceTradeInfo:sync` 权限，并校验交易对属于现货。

## 5. 底仓操作

现货统计页面可以从当前未平仓买入批次中选择并设置底仓。底仓管理接口包括：

```text
GET  /api/binanceSpotCorePosition/candidates?uid={uid}&symbol={symbol}
POST /api/binanceSpotCorePosition
PUT  /api/binanceSpotCorePosition/{id}
PUT  /api/binanceSpotCorePosition/{id}/release
```

- 新增：锁定指定买入成交的部分或全部剩余数量。
- 修改：调整仍有效的底仓数量和备注。
- 解除：写入 `released_at`，使这部分数量恢复为普通可撮合持仓。
- 删除：业务上禁止直接删除，避免丢失底仓历史。

准备卖出底仓时，必须先解除底仓或调小底仓数量，再同步卖出成交并执行 FIFO 撮合。解除操作本身只改变底仓状态，不会自动触发撮合；释放出的数量仍按原买入时间参与 FIFO。若卖出已经在没有足够可用买入的情况下被处理为 `EXCEPTION`，后续单独解除底仓不会自动重试，因为撮合器只读取 `PENDING` 和 `PARTIAL` 卖出。

历史数据需要重新建立撮合基线时，应使用显式维护流程：

1. 备份目标 `uid + symbol` 的撮合明细、撮合状态和底仓记录。
2. 清空该范围的撮合明细，并将原始成交重新初始化为待撮合状态。
3. 在执行 FIFO 前先设置需要保护的底仓批次和数量。
4. 执行一次 FIFO 撮合，再核对卖出异常数、剩余持仓数量和底仓数量。

不能先完成 FIFO 再补设底仓；已经写入的撮合关系不会因新增底仓自动重新分配。

## 6. 统计读取口径

现货统计不再执行内存 FIFO：

- 已实现盈亏、手续费、净盈亏和历史成交明细读取 `binance_spot_trade_match`。
- 实际持仓数量读取 `binance_spot_trade_match_state.remaining_qty`，包含当前有效底仓数量；底仓只从 FIFO 可用数量中扣除。
- 未匹配卖出数量根据卖出状态和撮合明细汇总。
- 当前现货价格复用统计接口返回的 `currentSpotPrice`，页面不再进行 5 秒价格轮询。
- 查询条件不再包含“截止日期”，历史撮合关系以数据库已固化结果为准。
- `tradeList` 按未平仓买入批次逐笔返回，必须保留各批次的 `openTime`；后端不按价格合并。同价买入和价格区间聚合由统计页面按展示需求处理。

底仓仍属于账户真实现货持仓，因此计入持仓数量、持仓成本和浮动盈亏；但不进入 FIFO 撮合候选。

因此统计与撮合使用两个不同口径：

- 展示持仓：直接使用买入状态的 `remaining_qty`，包含底仓。
- 撮合可用量：使用 `remaining_qty - active_core_qty`，不包含有效底仓。

统计页面的交互、图表口径和响应式布局详见[现货交易统计页面](./现货交易统计页面.md)。

## 8. 当前边界与后续事项

- 当前只处理普通现货 FIFO 平仓。
- 币本位合约开空后设置现货限价止损委托的对冲关系，需另行设计，不复用普通现货平仓撮合。
- 当前 `EXCEPTION` 卖出表示当次没有足够的历史可用买入完成撮合；处理异常数据前应先核对成交同步完整性和底仓设置。
- 不允许直接修改撮合明细或撮合状态 CRUD 数据；业务变更应通过同步、撮合和底仓接口完成。
- 如未来需要重算历史撮合，必须设计显式重放流程，不能在统计查询时隐式重算。
