# 交易分析模块

本文档记录 BTC 事件合约交易分析功能的业务背景、代码位置和重要实现约定，供后续开发接手时快速理解。

## 1. 模块目标

交易分析模块用于记录 BTC 事件合约每笔交易的开仓、平仓和复盘信息。当前用户主要操作 BTC，因此表中暂不维护交易标的字段。

核心目标：

- 记录交易方向、金额、开仓/平仓价格、开仓/平仓时间、盈亏金额。
- 记录开仓原因、入场类型、开仓评分、平仓复盘、交易质量和交易备注。
- 保存开仓和平仓时不同周期的 K 线截图。
- 支持通过币安订单截图 OCR 识别并自动回填部分表单字段。

## 2. 数据表

表名：

```text
invest_trade_analysis
```

当前实体字段位于：

```text
eladmin/eladmin-invest/src/main/java/me/zhengjie/invest/domain/InvestTradeAnalysis.java
```

主要字段：

- `id`：主键。
- `direction`：交易方向，必填，字典项。
- `amount`：交易金额。
- `entryType`：入场类型，字典项。
- `openTime`：开仓时间。
- `closeTime`：平仓时间。
- `openPrice`：开仓价格。
- `closePrice`：平仓价格。
- `netProfit`：盈亏金额。
- `openReason`：开仓原因。
- `openKlineImages`：开仓 K 线图片，存 JSON 字符串。
- `closeKlineImages`：平仓 K 线图片，存 JSON 字符串。
- `score`：开仓评分。
- `reviewConclusion`：平仓复盘。
- `qualityLevel`：交易质量，字典项。
- `remark`：交易备注。
- `createBy`、`updateBy`、`createTime`、`updateTime`：审计字段。

已明确不需要的字段：

- 交易编号：实际交易没有编号，暂不保存。
- 交易标的：当前只操作 BTC，暂不保存。
- 奖金支付率：不需要记录。
- 复盘状态：不单独保存；没有复盘结论即可视为未复盘。

## 4. 初始化和代码生成流程

该模块一开始应按项目原有流程走代码生成，而不是手写整套 CRUD。

推荐流程：

1. 先在数据库中创建 `invest_trade_analysis` 表。
2. 进入系统工具 -> 代码生成。
3. 导入或同步 `invest_trade_analysis` 表。
4. 配置生成信息：
   - 模块名称：`invest`
   - 功能名称：交易分析
   - 实体类名：`InvestTradeAnalysis`
   - 接口路径：`investTradeAnalysis`
   - 后端包路径保持 `me.zhengjie.invest`
   - 前端目录对应 `src/views/invest/investTradeAnalysis`
5. 配置字段展示、查询、必填、字典等生成属性。
6. 选择覆盖生成前后端基础代码。
7. 先确认基础增删改查可用，再做业务页面和 OCR 等定制。

注意：

- 如果生成出来的中文乱码，优先检查生成器、数据库连接、文件编码是否使用 UTF-8，再通过代码生成器重新覆盖生成，不要直接手改一堆乱码文件。
- 后续新增标准 CRUD 页面时也优先走代码生成器，生成后再微调。

## 5. 字典项

当前前端使用的字典：

- `invest_trade_analysis_direction`：交易方向，例如看涨、看跌。
- `invest_trade_analysis_entry_type`：入场类型。
- `invest_trade_quality_level`：交易质量。

字典项在系统管理 -> 字典管理维护。前端应使用项目现成字典机制，不要硬编码下拉选项。

## 6. 表单设计

表单不是默认生成器的简单表单，已经抽成单独组件：

```text
eladmin-web/src/views/invest/investTradeAnalysis/components/InvestTradeAnalysisForm.vue
```

当前表单分区：

- 订单识别
- 基础信息
- 开仓记录
- 平仓记录
- 复盘

字段顺序以当前表单为准：

1. 基础信息：交易方向、交易金额、开仓评分、交易质量。
2. 开仓记录：开仓 K 线、开仓价格、开仓时间、入场类型、开仓原因。
3. 平仓记录：平仓 K 线、平仓价格、平仓时间、盈亏金额。
4. 复盘：平仓复盘、交易备注。

表单注意事项：

- 价格、金额、盈亏等字段应限制为数字输入，盈亏金额允许正负号。
- 列表筛选项赋值后应主动查询。
- 筛选项、表格列、表单 label 需要保持命名一致。
- 保存按钮仍走 eladmin CRUD 组件原有提交流程。
- 表单组件通过 `validate`、`clearValidate` 等方法兼容父级 CRUD 表单引用。

## 7. K 线图片

需要记录开仓和平仓后的周期 K 线图：

```text
1D、4H、2H、1H、15M、5M
```

当前设计：

- 不单独建图片子表。
- 图片上传到对象存储或项目现有上传接口。
- 数据库字段 `openKlineImages`、`closeKlineImages` 直接保存完整图片 URL。
- 多周期图片以 JSON 字符串保存，例如：

```json
{
  "1H": "https://example.com/1h.png",
  "15M": "https://example.com/15m.png"
}
```

交互约定：

- K 线格子支持点击上传、粘贴上传、手动填写链接。
- 点击已有图片进入预览。
- 预览弹窗支持在不同周期图片之间切换。
- 订单截图上传和 K 线截图上传都支持粘贴时，需要注意粘贴目标冲突；当前通过 `pasteTarget` 和 `activeKlineTarget` 区分。

## 8. 订单 OCR

订单识别入口：

- 前端接口：`eladmin-web/src/api/investTradeAnalysis.js`
- 后端接口：`POST /api/investTradeAnalysis/ocr`
- Controller 只接收文件并调用 Service。
- 业务解析逻辑放在 `InvestTradeAnalysisServiceImpl`。

OCR 工具：

- 使用 `AliyunOcrUtil`。
- `AliyunOcrUtil.recognizeGeneral` 入参为 `File`。
- OCR 工具应放在 common 或通用能力中，返回通用 OCR 数据；交易分析模块负责把 OCR 数据解析成业务字段。

后端返回给前端的业务字段对象：

```text
InvestTradeAnalysisOcrVO
```

字段包括：

- `direction`
- `amount`
- `openPrice`
- `openTime`
- `closePrice`
- `closeTime`
- `netProfit`

重要约定：

- 前端不负责解析 OCR 原始文本。
- 后端 `/ocr` 接口应直接返回可回填表单的业务字段。
- 币安订单截图分为刚开仓截图和平仓后截图，字段不一定齐全。
- 方向识别会结合 OCR 文本和截图左上角图标颜色判断看涨/看跌。

前端交互：

- 表单顶部有“订单识别”区域，左侧上传订单截图，右侧展示识别结果。
- 上传或粘贴订单截图后主动识别。
- 保留“识别订单”按钮，作为自动识别失败时的手动入口。
- 标题区域有“识别剪贴板订单”按钮，可尝试直接读取剪贴板图片并识别回填。
- 识别结果需要点击“应用到表单”或自动应用后才写入主表单。

## 9. 复制 JSON

表单标题区域有“复制JSON”按钮，用于把当前表单内容复制出来，便于分享、排查或人工备份。

注意：

- 复制内容应是当前表单业务字段。
- K 线图片在提交前会从内部 map 同步为 JSON 字符串。
- 该功能不替代保存，只是复制当前表单状态。

## 10. 后续开发注意事项

- 不要把 `parseOrderOcr` 这类业务解析逻辑放在 Controller。
- 不要让前端解析 OCR 原始结果，前端只消费业务字段。
- 修改表字段时，需要同步实体、Mapper XML、QueryCriteria、前端 defaultForm、表单组件、列表列和导出逻辑。
- 修改字典值时，需要同步系统字典项，并确认前端 `dicts` 引用。
- 修改图片结构时，要兼容历史字符串值；当前 `parseKlineImages` 对旧单 URL 会兜底放到 `5M`。
- 不要随意重写 eladmin 原有 CRUD 机制，优先保持和项目现有组件一致。
- 涉及阿里云 OCR 配置时，不要提交明文 AccessKey；如需加密配置，使用项目已有 Jasypt 流程。
